## Critical correction from prior investigation

**Both keys in rvcas's system are P-256.** The earlier assumption
that the access key was secp256k1 was wrong. The access key is
independently generated via Web Crypto `P-256`, stored in
localStorage as JWK. Neither key is Midnight-compatible (secp256k1).

This means the rvcas system is an identity/authentication layer,
NOT a blockchain signing layer. The curve mismatch between P-256
(passkeys) and secp256k1 (Midnight) is an unsolved ecosystem gap.

## How rvcas midnightOS Passkeys actually works

**Source:** `git@github.com:rvcas/passkeys.git` (Cloudflare Worker)

### Two-key hierarchy (both P-256)

- **Root key (passkey):** P-256, generated by WebAuthn, hardware-backed,
  private key never leaves the authenticator
- **Access key:** P-256, independently generated via Web Crypto,
  exportable, stored in browser localStorage per credential ID

The access key is NOT derived from the passkey. It's a completely
separate keypair linked through the authorization mechanism.

### DID format: `did:key`

Standard W3C `did:key` method. Derived from the **access key**
(not the root passkey):

```
did:key:z<base58btc(0x8024 || compressed_P256_pubkey)>
```

- Multicodec prefix `0x8024` = P-256 public key
- `z` prefix = base58btc encoding (multibase standard)
- The DID Document contains only the access key as verification method

### keyAuthorization: server-attested, not self-verifiable

The authorization flow:
1. Server creates a challenge embedding the access key's public key
2. Passkey (in hardware) signs the challenge via WebAuthn ceremony
3. Server verifies the signature and stores an authorization record
4. The WebAuthn signature itself is **discarded** — only metadata kept

The authorization record is:
```
{ rootPublicKey, accessKeyPublicKey, credentialId, authorizedAt }
```

**This is a trust-the-server model.** Verifiers must trust
`passkeys.rvcas.dev` that the authorization is legitimate.

### webauthx (v0.1.1, by wevm)

Pure WebAuthn ceremony orchestration. Does NOT handle DIDs,
delegation, or access keys. All Midnight-specific logic is rvcas's
own code. Built on `ox/webauthn` from the Viem/Wagmi ecosystem.

## Android CredentialManager: two modes

### Mode 1: CredentialManager client (standard)

Your app calls the system to create/use passkeys. Google Password
Manager (or another provider) generates and holds the private key.
**You never see the private key.** You get the public key by parsing
the CBOR/COSE attestation response.

- Works on API 28+
- Passkeys auto-sync via Google Password Manager
- No control over key material

### Mode 2: CredentialProvider service (Kuira's path)

Your app registers as a credential provider. When ANY app requests
a passkey, the system can route to YOUR service. **You generate the
key, you store it, you control the crypto material.**

- Requires API 34+ (Android 14) for system discovery
- You generate P-256 keypairs yourself
- Full access to raw public AND private key bytes
- You handle your own storage and sync
- Needs `BIND_CREDENTIAL_PROVIDER_SERVICE` permission
- Needs Digital Asset Links (`.well-known/assetlinks.json`)

**For the SDK (standalone dApps):** Use Mode 1. The app calls
CredentialManager to create passkeys via whatever provider is
available (Google Password Manager on most devices). Public key
extracted from attestation for DID derivation.

**For Kuira (sigil manager):** Use Mode 2. Kuira IS the provider.
When installed, dApps route to Kuira for passkey operations. Kuira
generates keys in TEE/StrongBox with biometric binding.

### API level impact (minSdk 30)

| Capability | Min API | Our minSdk 30 |
|-----------|---------|---------------|
| CredentialManager client | 28 | ✅ Works |
| Passkey creation/auth | 28 | ✅ Works |
| CredentialProvider service | **34** | ⚠️ Only on Android 14+ |
| Third-party provider selection | 34 | ⚠️ Only on Android 14+ |

On API 30-33 devices, Kuira can create passkeys for its own use
but cannot be discovered as a provider by other apps. Fallback:
direct inter-app communication (bound service, deep links).

## Industry state of the art

### The P-256 → secp256k1 problem: three approaches

| Approach | Who ships it | How | Fits Midnight? |
|----------|-------------|-----|---------------|
| **A: Passkey as auth gate** | Turnkey, Privy, Capsule | Passkey authenticates to server/enclave which holds blockchain key | Needs a server — not self-custodial |
| **B: On-chain P-256 verifier** | Clave, ZeroDev (via RIP-7212) | Chain verifies P-256 natively | Midnight uses Schnorr/secp256k1 — blocked |
| **C: Passkey authorizes delegated key** | rvcas, **our sigil model** | Passkey authorizes secp256k1 access key via signed delegation | Best fit — self-custodial, works with Midnight |

### Best UX achieved today

- **Clave (zkSync):** One-tap passkey onboarding, no seed phrase ever.
  Passkey IS the account signer. Only works because zkSync has native
  P-256 verification.
- **Turnkey:** One-tap passkey auth, keys in AWS Nitro Enclaves. Best
  UX with server-side custody trade-off.
- **Biconomy session keys:** Per-dApp temporary signing keys with
  time/value/function constraints. Closest analog to our
  silent/notify/approve tiers — but simpler.

### What's still research

- **DRek social recovery:** Mentioned by Charles Hoskinson. No public
  spec. Don't build against it until a spec exists.
- **PRF extension on Android:** Chrome supports it. Native
  CredentialManager support is maturing. Could enable passkey-derived
  encryption keys for cloud backup.
- **Passkey-derived secp256k1 keys:** No standard. Math is
  straightforward (PRF output → HKDF → secp256k1 scalar) but
  requires a relying party for PRF, and determinism across devices
  needs real-world testing.

## Our advantage over rvcas

| Aspect | rvcas (web) | Kuira SDK (Android native) |
|--------|------------|---------------------------|
| Root key storage | Browser authenticator | TEE / StrongBox (hardware) |
| Access key storage | localStorage (cleartext JWK) | Android Keystore (encrypted) |
| keyAuthorization | Server-attested (trust rvcas) | **Self-verifiable** (TEE signs directly) |
| Biometric | Browser WebAuthn prompt | BiometricPrompt (native, customizable) |
| Cross-device | Platform-dependent | Google Password Manager sync |
| Curve support | P-256 only | P-256 (passkey) + secp256k1 (access key) |
| Offline signing | ❌ Needs server | ✅ Access key signs locally |

The biggest win: **self-verifiable keyAuthorization.** The TEE-backed
root key signs the delegation payload directly. Anyone can verify the
authorization cryptographically without trusting a server. rvcas's
model discards the WebAuthn signature and stores only metadata.

## Decisions needed

### 1. Access key curve: P-256 or secp256k1?

rvcas uses P-256 for both. Midnight needs secp256k1 for blockchain
signing. Options:

- **A: Access key is secp256k1.** Directly signs Midnight transactions.
  DID uses secp256k1 multicodec prefix (`0xe7`). Diverges from rvcas
  format but is immediately useful on-chain.
- **B: Access key is P-256 (match rvcas).** Requires a third key layer
  for blockchain signing (passkey P-256 → access key P-256 → signing
  key secp256k1). More complex, but interoperable with rvcas.
- **C: Both.** Access key is P-256 for identity/DID interop. A
  secp256k1 signing key is derived or generated alongside it, linked
  by the same keyAuthorization. The DID is P-256, the blockchain key
  is secp256k1.

**Recommendation:** A — access key is secp256k1. Simplest, immediately
useful. DID interop with rvcas can be handled by supporting both
multicodec prefixes in DID resolution. The ecosystem hasn't
standardized yet — we can help set the direction.

### 2. keyAuthorization: what does the root key sign?

The payload the P-256 root key signs to authorize a secp256k1
access key. Proposed structure:

```
{
  "action": "authorize-access-key",
  "rootPublicKey": "<compressed P-256 hex>",
  "accessKeyPublicKey": "<compressed secp256k1 hex>",
  "accessKeyCurve": "secp256k1",
  "scope": ["midnight:sign", "midnight:read"],
  "authorizedAt": <unix timestamp ms>,
  "expiresAt": <unix timestamp ms or null>
}
```

The P-256 signature over this JSON (SHA-256 hash → ECDSA sign in TEE)
is the self-verifiable authorization. Anyone with the root public key
can verify it. No server needed.

### 3. DID derivation: from which key?

rvcas derives the DID from the access key. Options:

- **A: DID from access key.** Matches rvcas. The DID represents the
  dApp-scoped identity. Multiple DIDs per user (one per dApp).
- **B: DID from root passkey.** The DID represents the user's root
  identity. One DID per user, stable across dApps. Access keys are
  subordinate.
- **C: Both.** Root DID (from passkey) + per-dApp access DIDs. The
  keyAuthorization links them.

**Recommendation:** C — both. Root DID is the sigil identity (stable,
cross-app). Access DIDs are per-dApp (scoped, revocable). This maps
cleanly to the sigil model: one sigil, many delegations.

### 4. Recovery: what happens when the device is lost?

What syncs automatically:
- Passkey (P-256) → Google Password Manager sync ✅

What does NOT sync:
- secp256k1 access keys (device-local)
- Android Keystore keys
- App internal state

Options:
- **Encrypted cloud backup:** Passkey authenticates → download
  encrypted blob from Block Store / GDrive → decrypt with PRF-derived
  key or passkey-authenticated server key
- **Re-derivation from seed:** If the user backed up a seed phrase,
  access keys can be re-derived on the new device
- **Passkey-only recovery (future):** If PRF extension stabilizes on
  Android, the passkey's PRF output can deterministically derive
  secp256k1 keys. No seed needed. But PRF support is still maturing.

**Recommendation:** Ship with encrypted cloud backup (Phase 8C).
Investigate PRF-based re-derivation as a future path. Keep seed
phrase as a power-user escape hatch.

## How this maps to the SDK tiers

### Tier 1 — Standalone dApp (SDK)

1. App calls CredentialManager (Mode 1) to create a passkey
2. Public key extracted from attestation → root DID derived
3. SDK generates secp256k1 access key locally
4. Root key signs keyAuthorization (via CredentialManager auth ceremony)
5. Access key signs Midnight transactions directly
6. Identity = root DID + access key + keyAuthorization

### Tier 2 — Kuira installed (upgrade)

1. Kuira is registered as CredentialProvider (Mode 2, API 34+)
2. dApp's CredentialManager call routes to Kuira
3. Kuira generates passkey in TEE/StrongBox
4. Kuira signs keyAuthorization with biometric gate
5. Access key managed by Kuira's sigil system
6. Match appears in My Sigil tab as "bearing your sigil"
7. Same root DID, same access key — just better hardware backing
